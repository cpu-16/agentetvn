# Executable development evaluation

Run `bun run --no-env-file test:evaluation`. Reports and reused-suite logs stay in ignored `db/evaluation-dev/`.

Scenarios are specifications for tests, not application queries. The runner executes real agenda, indicator, grouping, consultation and draft functions. It reuses T01–T10 and shares their existing synthetic fixture definitions. Each report includes the exact commit, working-tree state, execution-definition hash, fixture hash, source-definition hashes, actual outputs, deterministic checks and case status. A dirty-tree report identifies uncommitted definitions; rerun after committing for evidence tied to a clean exact commit.

CU01 checks a synthetic expected order and the existing public snapshot's structural contract: five eligible topics, diversity, trusted original source bindings, reasons and gaps. It does not establish human ranking relevance. CU05 asks which public logistics signals should be reviewed. It supplies an explicit synthetic logistics fixture and checks sector context and verification gaps; it does not produce a client score or definitive regulatory alert. The draft target checks the complete 250-word limit, three questions, both conflicting source versions, marked hypotheses and missing evidence. Human banking usefulness remains pending.

The figure scenario supplies an explicit selected indicator ID. Its synthetic 2023 value is a test value, not a measured public fact. Missing source context is refused rather than silently choosing a country or year. Agency replication, missing-value abstention, source injection and a deliberately changed claim use marked synthetic fixture provenance. Candidate fixture records can carry `sintetica=false` to model eligible public inputs; their evaluation provenance remains synthetic.

Citation identity and source support are different metrics. `citation_existence` checks whether the cited ID exists. `citation_field_constraints` binds facts to the original selected source field and checks permitted scope, numeric values, names, quotations and causal wording. The negative-control case deliberately retains a valid ID while changing its number to the competing publication's number: existence remains 1, field support drops, and the actual banking validator must reject it. These deterministic constraints are not a semantic entailment score. No human gold labels, precision, macro-F1 or banking correctness scores are fabricated. Empty factual-claim denominators are unscored, not perfect scores.

The Notion failure/correction scenario remains manual pending until a genuine recorded failure, correction commit, passing rerun and verified Notion link exist. A synthetic failure or an induced exit-code probe cannot establish that historical proof. Independent human semantic acceptance is also manual pending. Full embedding inference is reported separately and is not inferred from lexical fallback or a skipped model test.

The worker discards inherited service credentials, never loads environment files, forces tracing off and blocks fetch. Reused suites create fresh disposable databases and allow only loopback test doubles. No model download, reserved or development benchmark run, ingestion, user-database migration, publication, Notion write or trace upload occurs.

`scripts/evaluation/langsmith.ts` exports raw local target/evaluator interfaces. Do not upload those raw outputs. `scripts/evaluation/technical.ts` separately projects executable results into case IDs, fixture hashes, counts, statuses and deterministic feedback. Empty factual denominators remain unscored; the negative control correctly has less than perfect field support while its rejection contract passes.

The separately authorized cloud runner is `bun --env-file=.env.local run scripts/evaluate-langsmith-development.ts --approved-development-evaluation`. It refuses a dirty tree and creates one `AgenteTVN-dev-<commit>-<timestamp>` development dataset and experiment in the existing AgenteTVN workspace. Existing credentials are loaded by Bun and never copied to tests or reports. Only the approved LangSmith API endpoint is allowed. The experiment has one repetition and one root per runnable case; no model or external judge is called. Reference examples contain only case IDs and fixture hashes, with a technical expected status. Questions, source text, country/year selections and generated prose are resolved and evaluated locally. Manual evidence cases are excluded, not marked passing. Offline/default application tracing remains disabled.

Actual function calls produce child stages for development-case dispatch, agenda selection, indicator construction, grouping, drafting, citation validation, contract validation and reused tests. Consultation is separate from retrieval: rule-based abstention does not emit a retrieval stage, while the lexical case traces the real BM25 search. Spans do not imply unexecuted embedding inference or LLM work. The transport removes raw inputs, runtime, prompts, events, serialized objects and errors and restricts metadata to approved technical fields. It preserves reference-example IDs only in the scoped development experiment.

The runner reads back persisted runs, independently counts roots and children, checks their parentage and expected executed stages, validates technical payloads, verifies the experiment's reference dataset, and reads each recorded feedback item. Results and direct project/dataset links stay in ignored `db/evaluation-dev/cloud-experiment.json`. A raw question dataset without real executions and feedback does not establish evaluation evidence. A single connection trace alone does not establish scenario quality.

SDK interfaces and experiment format: [evaluation targets and evaluators](https://docs.langchain.com/langsmith/evaluate-llm-application).
